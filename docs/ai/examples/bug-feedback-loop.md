# 示例：数据恢复 Bug 的反馈循环

## 问题整理

- 实际行为：用户选择合法备份并确认恢复后，界面提示失败，但当前工作区数据是否已被部分替换无法确认。
- 预期行为：保存成功时完整替换；保存失败时恢复导入前的内存文档并保留错误状态。
- 环境：Web IndexedDB 或 Tauri 本地文件驱动；具体运行环境必须从报告或复现结果确认。
- 最小复现：为 storage driver 注入一次稳定的保存失败，执行 `replaceDocument()`，观察文档快照和错误状态。

这只是反馈循环示例，不代表仓库当前存在该 Bug。无法从报告、测试或运行结果确认的条件必须写成“待业务确认”。

## 修复前反馈循环

优先添加目标测试，使用失败的 storage driver 调用 `replaceDocument()`，断言导入失败后仍保留旧文档。测试必须在修复前因原始问题失败，并记录命令、退出码和失败断言。

如果只能在特定 Tauri 文件系统环境复现，则记录：

- 无法自动化的具体边界。
- 不含真实作品或 API Key 的固定测试数据。
- 从选择备份到确认恢复的稳定人工步骤。
- 可观察证据，例如脱敏错误信息、页面状态和导入前后摘要。

## 修复与回归

只在反馈循环捕获原始症状后实施最小修复。使用完全相同的测试、命令、脚本或人工步骤确认修复后通过，并保留回归测试；无法保留时记录原因和未覆盖风险。

## REVIEW 结论规则

- 同一反馈循环修复前失败、修复后通过：可以报告原始 Bug 已修复。
- 只证明相邻代码行为变化：报告具体变更，不声称原始 Bug 已修复。
- 原始症状无法复现：报告调查结果、假设和下一步，不实施或宣传推测性修复。
