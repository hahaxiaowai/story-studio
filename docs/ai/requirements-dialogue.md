# 需求澄清对话

## 目标

DEFINE 不是一次性填写模板，而是把模糊需求逐轮收敛为可验证的 Spec。每轮优先解决一个会改变范围、业务规则、方案或验收方式的关键决策，并在得到回答后同步 Spec 草稿。

## 对话流程

```text
原始需求
→ 读取相关 Architecture / Feature / ADR 和源码证据
→ 区分已确认事实、假设和未知项
→ 每轮确认一个关键决策
→ 更新 Spec 草稿
→ 核对数据模型、主流程和异常场景
→ 用户确认 Spec
→ 进入 PLAN
```

开始提问前，先从仓库确认能够发现的事实，不向用户询问代码、类型、入口或测试中已经有答案的问题。需要用户决定时，说明当前证据、可选方案及其影响；不同决策不合并成一个宽泛问题。

## 澄清维度

- 用户与目标：谁使用、解决什么问题、如何判断有价值。
- 入口与前置条件：从哪里进入，依赖哪些工作区、内容、模型或运行环境状态。
- 核心路径：用户动作、系统响应、状态变化和完成结果。
- 业务规则：数量、优先级、重复操作、幂等和生命周期。
- 异常路径：失败、取消、中断、重试、数据缺失和兼容行为。
- 契约影响：`StudioDataDocument`、模块状态、导航、Tauri/Web 和 AI transport。
- 交付边界：范围、非目标、成功标准、验收示例和验证证据。

## 问题记录

所有会影响实现的澄清项写入 Spec：

```text
问题 | 状态 | 当前结论 | 依据 | 对范围的影响
```

状态只允许：`待确认`、`已确认`、`不适用`、`推迟到后续 Spec`。代码、测试和当前文档无法证明且用户尚未确认的业务含义，必须标记“待业务确认”。

## 停止追问条件

- 影响范围、核心流程、关键规则、主要状态和异常行为已经明确。
- 范围与非目标没有冲突。
- Feature、Plan 和 ADR 的影响已经判断。
- 成功标准能够由测试、命令或明确人工步骤验证。
- 剩余未知项不会实质改变方案，且已推迟或记录为风险。

小型、低风险且行为明确的修改可以走简化 DEFINE，但仍要确认外部行为、失败行为和验证方式。
