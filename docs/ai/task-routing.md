# AI 任务分流

先判断任务类型，再进入统一的 `DEFINE → PLAN → BUILD → VERIFY → REVIEW → SHIP` 生命周期。任务路径只调整流程重量，不创建第二套状态系统。

| 任务类型 | 执行路径 | 进入 BUILD 的门禁 |
| --- | --- | --- |
| 模糊新功能 | 需求澄清 → Spec → Plan → 垂直任务拆分 | Spec 已确认，关键未知项已关闭或明确推迟 |
| 明确的中大型功能 | Spec → Plan → Build → Verify → Review | 范围、异常行为和验收标准明确 |
| 小改动 | 行为确认 → 目标验证 → Build → Review | 外部行为、失败行为和验证方式明确 |
| Bug | 问题整理 → 原始症状反馈循环 → 修复 → 回归验证 | 已捕获原始症状，或已记录无法自动化的原因和稳定人工路径 |
| 重构 | 行为保持标准 → 小步计划 → 测试保护 → 分步重构 | 现有行为和保护测试明确，每一步可独立验证和回退 |
| 架构探索 | 现状证据 → 候选问题 → 取舍确认 → ADR 或重构 Spec | 只探索时不进入 BUILD；改变长期边界后新建 Spec |
| docs-only | 事实来源确认 → 文档修改 → 结构和链接验证 | 事实来源和不修改产品代码的边界明确 |

## 垂直任务规则

Plan 中的 Task 按可独立验收的用户路径或行为切片，不按“先页面、再状态、最后测试”等纯技术层横向拆分。每项 Task 必须包含验收标准、验证方式、依赖、预计影响文件和规模；规模为 L 时继续拆分。

## Bug 反馈循环

修复前记录实际行为、预期行为、环境和最小复现步骤，并建立测试、命令、脚本或稳定人工路径捕获原始症状。自动化反馈应在修复前失败、修复后通过；不能自动化时记录原因、人工步骤和未覆盖风险。没有捕获原始症状时，只能报告调查结果或推测性变更，不能声称 Bug 已修复。

完整样例见 [`examples/bug-feedback-loop.md`](./examples/bug-feedback-loop.md)。
