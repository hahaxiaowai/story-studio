# AI 任务分流

先判断任务类型和风险等级，再进入统一的 `DEFINE → PLAN → BUILD → VERIFY → REVIEW → SHIP`。任务路径只调整流程重量，不创建第二套状态系统。

## 风险等级

| 等级 | 典型范围 | 默认文档 |
| --- | --- | --- |
| XS | 文案、局部样式、明确的测试修正 | 对话内 Micro Spec；通常不新建 Spec/Plan |
| S | 单模块、行为和失败边界明确 | 精简 DEFINE；需要跨会话或多 Task 时才新建 Plan |
| M | 用户可见流程、跨模块状态或多阶段交付 | 完整 Spec、结果契约式 Plan |
| L | schema、Tauri/Web、AI transport、安全、不可逆数据或长期架构 | 完整 Spec/Plan、ADR 判断、独立 Review 和真实运行证据 |

文件数量只是提示，不决定风险等级。数据不可逆性、运行时边界、安全、用户影响和回滚难度任一升高时，应升级流程重量。

## 任务路径

| 任务类型 | 执行路径 | 进入 BUILD 的门禁 |
| --- | --- | --- |
| 模糊新功能 | 需求澄清 → Spec → Plan → 垂直任务 | 关键未知项已关闭或明确推迟 |
| 明确的中大型功能 | Spec → Plan → Build → Verify → Review | 范围、异常行为和验收明确 |
| 小改动 | Micro Spec → 目标验证 → Build → Review | 外部行为、失败行为和验证方式明确 |
| Bug | 问题整理 → 原始症状反馈循环 → 修复 → 回归验证 | 已捕获症状，或记录稳定人工路径和限制 |
| 重构 | 行为保持标准 → 小步计划 → 测试保护 → 分步重构 | 现有行为和保护测试明确 |
| 架构探索 | 现状证据 → 候选问题 → 取舍确认 → ADR 或 Spec | 只探索时不进入 BUILD |
| docs-only | 事实来源确认 → 文档修改 → 结构和链接验证 | 事实来源和只改文档的边界明确 |

## 连续执行和确认

- 用户确认 Spec/Plan 或明确说“执行”后，在既定范围内连续完成后续 Task，不在内部步骤间重复询问。
- 产品含义仍有多种合理选择、范围或架构发生实质变化时，先回写 Spec/Plan，再请求决策。
- commit、push、发布、删除、外部消息和其他有副作用动作继续遵循各自确认规则。

## 垂直任务规则

Plan 中的 Task 按可独立验收的用户路径或行为切片。每项只保留用户可观察结果、契约、验收、验证、风险、依赖和预计影响模块。函数签名或代码片段只用于固定协议、安全边界、迁移格式等不能自由调整的契约。

## Bug 反馈循环

修复前记录实际行为、预期行为、环境和最小复现步骤，并建立测试、命令、脚本或稳定人工路径捕获原始症状。没有捕获原始症状时，只能报告调查结果或推测性变更，不能声称 Bug 已修复。
