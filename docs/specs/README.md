# Spec 文档规则

`docs/specs/` 存放 Spec-Driven Development 的规格文档。Spec 描述一次将要实施或已经实施的变更，不替代 `docs/features/` 中的功能现状说明。

## 何时新增或更新 Spec

以下场景应先写或更新 Spec：

- 新增功能。
- 较大行为调整。
- 涉及持久化 schema、跨模块状态流或 Tauri/Web 边界。
- 改变用户主流程、导航入口或 AI 生成链路。

小修小补可以不写完整 Spec，但仍应在代码和文档中保持边界清晰。

## 建议结构

- 背景
- 目标
- 范围
- 非目标
- 用户流程
- 数据模型
- UI 结构
- 技术方案
- TDD 测试点
- 验收标准
- 验证命令
- 文档同步
- 完成记录

## 与计划文档的关系

- Spec 说明“要做什么”和“验收什么”。
- `docs/plans/YYYY-MM/*.md` 说明“怎么拆步执行”和历史状态。
- 旧计划和旧 Spec 不强制迁移；新功能优先从 Spec 开始，再拆到计划。

## 完成后回填

实施完成后，应在相关 Spec 中记录：

- 实际完成内容。
- 验证结果。
- 完成时间。
- commit 或本地变更说明。
- 未覆盖风险。

如果功能现状发生变化，还应同步更新 `docs/features/*.md`。

## 模板

新建 Spec 时优先复制 `docs/specs/_template.md`，再删除与本次无关的条目。不要留下空泛占位内容；不涉及的部分要写明“不涉及”和原因。
